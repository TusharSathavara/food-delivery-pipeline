# Section A — Concept Application

## A1 — Data Science Lifecycle

**Problem Definition:** The business problem is to predict which restaurant zones will have peak demand between 7–9 PM. The deliverable is a precise problem statement containing the target, time window, business users, and success criteria. **Data Collection:** The team gathers two years of order data and relevant fields such as timestamp, restaurant zone, order volume, and possibly day-of-week information. The deliverable is a documented raw dataset and data dictionary. **Data Preparation:** Missing values, duplicates, inconsistent zone names, and timestamp formats are cleaned. The deliverable is a reliable modelling dataset. **Exploration:** The analyst examines demand by zone, time, weekday, season, and other patterns using summaries and visualisations. The deliverable is an EDA report identifying useful patterns and candidate features. **Modelling:** Suitable prediction models are trained on historical features to estimate 7–9 PM demand. The deliverable is a trained model and its configuration. **Evaluation:** Predictions are compared with held-out historical data using suitable metrics and business thresholds. The deliverable is an evaluation report stating whether the model is reliable enough for operational use. Generative AI can accelerate **data preparation** by suggesting cleaning code or spotting inconsistent fields, but it may invent transformations or silently remove useful data, so a human must validate every change. It can also accelerate **exploration** by drafting analysis code and suggesting patterns to investigate, but it may produce incorrect interpretations or misleading code, so the analyst must verify results against the actual dataset.

## A2 — Git Branching Strategy

The team should keep `main` stable and give each developer a separate feature branch. A typical sequence is `git checkout main`, `git pull origin main`, and `git checkout -b feature/data-cleaning` for the first teammate, with equivalent names for the reporting and order-tracking work. After changes, each developer runs `git add .` and `git commit -m "feat: ..."`, then `git push -u origin feature/<name>`. The developer opens a Pull Request from the feature branch into `main`, and teammates review the changes before approval. After the review, the PR is merged and the local repository can run `git checkout main` and `git pull origin main`. A realistic conflict could occur if two developers edit the same function or shared configuration line. Git marks the conflicting sections with conflict markers, after which the developer decides which logic should remain, removes the markers, runs tests, and commits the resolution. This workflow prevents unfinished work from directly breaking `main` while allowing developers to work in parallel.

## A3 — map(), filter(), and reduce()

A named function should contain the commission rules so the calculation has one clear, reusable definition. For example, `calculate_commission(amount)` can return one percentage for small orders, another for medium orders, and a higher percentage for large orders. `map()` can then apply that named function through a lambda to every record, producing calculated fees without writing a second explicit loop for the transformation. This makes the operation compact and directly expresses the idea of transforming every item in a collection. `filter()` is useful when finance wants only records whose calculated fee is above an audit threshold, because it keeps only records satisfying a condition. `reduce()` can combine the resulting fee values into one accumulated total. For example, a reducer can repeatedly add each record's fee to a running total. The important design point is that the business rule remains in the named function while the higher-order functions describe how the collection is processed.

## A4 — Inheritance and Method Overriding

A base `User` class can contain common information such as an identifier and name, while `Customer`, `DeliveryPartner`, and `Admin` inherit from it. Each subclass can override `display_profile()` so the same method call produces the profile summary appropriate to that user type. This avoids duplicating shared attributes and lets the loop treat all users uniformly. If `display_profile()` is defined only on some subclasses and the base class does not provide it, a mixed list containing a plain `User` object can raise `AttributeError` when the loop calls the missing method. That runtime failure means the loop is not safe for future subclasses either. A better design is to define `display_profile()` on the base class as the common interface, with a sensible default implementation or an explicitly defined abstract method. Each concrete subclass then overrides it. With that contract, every valid user object has the method, so the mixed loop can call `user.display_profile()` without checking the class type.

## A5 — HTTP Status Codes and Safe File Writing

HTTP `200` means the request succeeded, so the script can process the response body. `401` means the request is unauthorized, usually because authentication credentials are missing or invalid, so the program should report the authentication problem rather than treating the response as successful data. `429` means too many requests, so the script should respect the API's rate limit and may retry after an appropriate delay. `500` is a server-side error, so the program should report that the remote service failed and avoid treating the response as valid business data. The file-writing operation should be placed inside a `try` block, with an `except` block handling an exception and a `finally` block performing cleanup or a completion message. The `finally` block runs whether the protected code succeeds or raises an exception. It therefore provides a reliable place for actions that must happen regardless of the result. For stronger file integrity, writing to a temporary file and replacing the destination only after a successful write can also prevent partial output.

## A6 — Regular Expressions for Phone Validation

The `re` module can validate and extract correctly formatted phone numbers from raw text by defining a pattern that describes the accepted structure. The pattern should specify the expected country or local prefix, the number of digits, and any permitted separators such as spaces or hyphens. Anchors can be used when validating a complete individual entry so that extra characters are not accepted before or after the number. `re.findall()` is more appropriate when the input is a larger block of text and the goal is to collect every matching valid entry, because it returns all non-overlapping matches. `re.search()` is designed to find the first matching location and therefore does not by itself extract the complete set of valid entries. A naive pattern might reject a valid number written with optional spaces or a country-code format, or accept an invalid number because it checks only the number of digits and not the allowed prefix. Therefore the exact business formatting rules should be confirmed before finalising the regular expression.
